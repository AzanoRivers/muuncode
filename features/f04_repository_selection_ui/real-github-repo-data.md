# Additional scope: Real GitHub Repository Data

Additional round on `f04`, not a new feature, per `CLAUDE.md`'s adjustment-vs-new-
feature rule: this replaces the stage-1 mockup's fake data with the real GitHub API
calls the feature has always been building toward (every placeholder handler in this
feature is already commented `// TODO(f04-stage-2): ...`, this round is that stage 2).

Two things become real: **listing** the signed-in GitHub account's actual
repositories (replacing `RepoSelector.tsx`'s hardcoded `MOCK_REPOS` array), and
**creating** a new repository from `CreateRepoForm`'s fields (replacing its
`console.info` placeholder). Everything else already built in this feature (the
accordion UI, the "Siguiente" button, its enabled/disabled logic, the visual design)
stays exactly as it is; only the data feeding it changes from fake to real.

## Architecture: same server-side-proxy pattern as `check-installation.ts`

`CLAUDE.md`'s original "File Storage and Access" section describes calling GitHub's
REST/Git Data API "directly from the browser" via Octokit. In practice, the one real
GitHub API call already built in this project (`api/check-installation.ts`) does
**not** do that: it is a small Vercel serverless function that receives the user's
access token from the browser and calls `api.github.com` itself, server-side,
returning a small JSON answer. This was the practical choice already made once
real GitHub API calls were actually implemented (GitHub's REST API does not reliably
send CORS headers for authenticated requests from an arbitrary browser origin, which
a direct `fetch()` from the browser needs). This round continues that same,
already-proven pattern for both new calls, rather than reopening the
direct-Octokit-from-browser question. Both new endpoints need only the user's own
access token (never the App's Client Secret), exactly like `check-installation.ts`.

## New endpoint 1: list repositories

- `api/list-repos.ts`, following `api/check-installation.ts`'s exact shape
  (`applyDevCors` first, `POST` only, `{ accessToken }` in the body, no Client
  Secret).
- Calls `GET https://api.github.com/installation/repositories` using an
  **installation access token**, not the user's own OAuth token: the
  `/user/installations/{installation_id}/repositories` endpoint (usable with the
  user's OAuth token directly) only lists repositories for *that one* installation
  and needs the installation id already known; simpler and more robust to mint a
  short-lived installation token server-side (`POST
  /app/installations/{installation_id}/access_tokens`, which *does* need the
  GitHub App's private key/JWT, held only server-side, never sent to the browser)
  and use it for the actual repo listing call. This means `list-repos.ts` needs:
  1. The user's access token, to find *which* installation belongs to this user
     (reuse `GET /user/installations`, same call `check-installation.ts` already
     makes, to get the `installation_id`).
  2. The GitHub App's private key (already generated by the user outside this repo
     per `f03`; needs a new environment variable, e.g. `GITHUB_APP_PRIVATE_KEY`, and
     the numeric `GITHUB_APP_ID`, both server-only) to mint a short-lived JWT, then
     exchange it for an installation access token.
  3. That installation token to call `GET /installation/repositories`.
- Returns a small, mockup-shaped JSON array (`{ id, name, private }[]`, matching
  `RepoSelector.tsx`'s current `MockRepo` shape closely enough that the frontend
  change is mostly "swap the data source", not a redesign) rather than GitHub's full,
  verbose repository object.
- **Decided**: step 2's JWT-signing + installation-token exchange uses
  `@octokit/auth-app`, added via `pnpm add @octokit/auth-app` (root `package.json`,
  alongside the existing `@vercel/node`/`typescript`/`@types/node` devDependencies
  that already type-check `api/*.ts`; this is a runtime dependency, not a dev one,
  since `api/lib/githubAppAuth.ts` actually calls it). Chosen over hand-signing a
  JWT with a generic JOSE library (e.g. `jose`): `@octokit/auth-app` is the official,
  purpose-built GitHub App auth strategy, maintained by GitHub itself, and handles
  the JWT claims (including the `iat` clock-skew margin GitHub expects), the
  installation-token exchange request, and caching/renewal of that token
  (installation tokens last about an hour) all in one call, rather than requiring
  this project to hand-roll and re-verify each of those details itself. Usage
  shape: `createAppAuth({ appId, privateKey })({ type: 'installation',
  installationId })` resolves to `{ token, expiresAt, ... }`; `api/lib/
  githubAppAuth.ts` wraps this, reading `GITHUB_APP_ID`/`GITHUB_APP_PRIVATE_KEY`
  from the environment (both already present in `.env`/`.env.example`), and, like
  every other helper in this feature, returns `null` on any failure rather than
  letting `@octokit/auth-app` throw past this project's boundary (per the global
  no-throw rule: wrap its call in a `try/catch` immediately, converting to a
  controlled return, since a third-party library throwing is exactly the
  documented, unavoidable exception case for that rule).

## New endpoint 2: create a repository

- `api/create-repo.ts`, same shape again. Body: `{ accessToken, name, description,
  isPrivate }` (matching `CreateRepoForm`'s existing fields exactly, including its
  own `MIN_NAME_LENGTH = 8` and space-to-hyphen behavior, which stay front-end-only
  UX rules, not something this endpoint re-validates beyond basic presence checks).
- Calls `POST https://api.github.com/user/repos` with the user's own access token
  (no installation token needed here, this is a plain user-to-server call):
  `{ name, description, private: isPrivate, auto_init: true }`. `auto_init: true` is
  deliberate: an empty repository with zero commits/branches would complicate the
  future feature that actually reads/writes files into it via the Git Data API.
- If the GitHub App's installation is scoped to "selected repositories" (not "all
  repositories"), a newly created repo is **not** automatically covered by it: this
  endpoint must also call `PUT
  /user/installations/{installation_id}/repositories/{repository_id}` right after
  creation, using the user's own OAuth token (this specific endpoint accepts a
  user-to-server token, no installation token needed), so the new repo is
  immediately usable by MuunCode. Needs the same `GET /user/installations` lookup as
  endpoint 1 to find the installation id (share that logic, do not duplicate it, see
  "Shared logic" below). If the App is already scoped to "all repositories" for this
  account, this call is a harmless no-op (GitHub returns success either way);
  detecting which mode the installation is in ahead of time is not required, always
  attempting the add-repository call is simpler and safe.

## Shared logic

- A new `api/lib/githubInstallationId.ts` (or similar), used by both new endpoints,
  wrapping the `GET /user/installations` call to resolve the `installation_id` for
  the signed-in account. `check-installation.ts` currently makes this same call
  itself for a different purpose (checking `total_count > 0`); consider whether it
  should be refactored to use this shared helper too, or left as-is since its need
  (a boolean) is simpler than the other two endpoints' need (the actual id) --
  decide during implementation, not a hard requirement either way.
- A new `api/lib/githubAppAuth.ts` (or similar) for endpoint 1's JWT-signing +
  installation-token exchange, kept separate from `api/lib/githubOAuth.ts` (which
  handles the user-facing OAuth token exchange/refresh, a different concern).

## Frontend changes

- `front/src/lib/githubRepos.ts` (new, mirroring `githubInstallation.ts`'s existing
  shape): `listRepos(accessToken)` and `createRepo(accessToken, { name, description,
  isPrivate })`, both returning `null` on any failure (never throwing, per this
  project's global no-throw rule), calling the two new endpoints via `apiUrl(...)`.
- `RepoSelector.tsx`: replaces the hardcoded `MOCK_REPOS` array with a real fetch on
  mount (via `listRepos`, using the access token `Station.tsx` already has). This
  introduces states this component has never needed before: loading (while the
  fetch is in flight) and error (the fetch failed). Needs a small loading indicator
  and an error state within the existing-repo accordion section specifically (the
  rest of the screen, including the create-new section, is unaffected by this).
  Follow this project's existing visual language for these two states (e.g. reuse
  `StatusScreen`'s icon+message pattern conceptually, or a simpler inline treatment
  scoped to just this section: decide during implementation based on what actually
  fits the compact card, do not force-fit a full-page pattern into a small area).
- `RepoSelector.tsx`'s `handleCreateRepo`/`CreateRepoForm`'s validity plumbing: on a
  real "Siguiente" click in create mode, calls `createRepo` with the form's actual
  values (previously never threaded past `CreateRepoForm` itself, since nothing
  needed them; the spec for the earlier "Repository Creation Accordion" round
  explicitly deferred this, see that file's "Component structure" section). This
  needs `CreateRepoForm` to expose its current field values upward (e.g. via a
  second callback, or lifting the fields' state the same way `selectedRepoId`
  already lives in `Station.tsx`, whichever reads cleaner) -- decide during
  implementation, not prescribed here.
- What happens after a successful create/select (navigating into an actual IDE view)
  stays explicitly out of scope: no real IDE view exists yet. A successful call this
  round just needs to reach a clear, real success/failure state, not navigate
  anywhere further.

## Explicitly out of scope for this round

- Any real IDE view or file-editing UI to navigate into after selecting/creating a
  repository (a separate, later feature).
- Real-time validation of the repo name against GitHub's actual naming rules beyond
  the existing `MIN_NAME_LENGTH` UX rule (e.g. checking for name collisions before
  submitting) -- GitHub's own API error response on a real collision is sufficient
  for this round; a nicer, live "name already taken" check can be a later polish
  round if wanted.
- Pagination of the repository list (if an account has many repos, `GET
  /installation/repositories` paginates; handling more than one page is deferred
  unless the user's own account/org has enough repos to make this immediately
  necessary to test).

## Round 2: sort by recent activity, and let the rocket loader own the initial fetch

Two corrections after the first round's `reviewer-light` approval:

1. **Every repo shows the same static "Reciente" label, and the list has no
   meaningful order.** `RepoListItem`'s `repoUpdatedPlaceholder` i18n key is a
   fixed string, never real data. GitHub's repository object already includes
   `pushed_at` (last code push, the right signal for "recent activity" in a
   coding context, as opposed to `updated_at` which also reflects metadata-only
   changes like a starred/renamed event). Fix: `api/list-repos.ts` includes
   `pushed_at` in its response and sorts the array by it (most recent first)
   before responding, so the frontend never has to re-sort; `front/src/lib/
   githubRepos.ts`'s `Repo` type gains `updatedAt: string` (the same field,
   renamed to match this project's camelCase convention); a new small utility
   (e.g. `front/src/lib/formatRelativeTime.ts`) formats that ISO date into a
   real, localized relative-time string ("hace 2 días" / "2 days ago") using
   the platform-native `Intl.RelativeTimeFormat` (no new dependency needed,
   and it already knows how to pick the right time unit and pluralization),
   fed the current i18next language so it matches whichever locale the rest of
   the UI is in. `RepoListItem` receives `updatedAt` as a prop and renders the
   computed label instead of the static placeholder. The now-dead
   `repoUpdatedPlaceholder` key is removed from both locale files.
   `api/create-repo.ts`'s response should include the same `pushed_at` field
   for shape consistency, even though a freshly created repo does not
   currently get inserted into the visible list (it just reaches the
   success-message state, per this round's own existing scope).

2. **The initial repo fetch should be covered by the same rocket-launch loader
   already used for the OAuth exchange, not `RepoSelector`'s own small inline
   spinner.** Currently `Station.tsx` transitions straight to `'success'` the
   moment `hasInstallation` is confirmed true, and `RepoSelector` independently
   fetches the repo list on its own mount, showing its own loading/error UI
   scoped to just the existing-repo accordion section while that happens. The
   user wants the *first* load folded into the same full-screen `LaunchLoader`
   sequence that already plays during sign-in, so the success screen only ever
   appears once the repo list is actually ready, and a failure reaches the same
   full-screen, already-designed red `StatusScreen` error view (`"Houston,
   tenemos un problema..."`) instead of a small in-card error message.
   Concretely: `Station.tsx`'s effect chain calls `listRepos(token)` right
   after `resolveInstallationStatus` confirms `hasInstallation`, still inside
   the `'exchanging'` status (i.e. before `transitionTo('success')`), and only
   transitions to `'success'` once that call resolves with real data,
   passing the fetched array down to `RepoSelector` as a new `repos: Repo[]`
   prop; if it returns `null`, transitions to `'error'` instead (reusing that
   status/screen exactly as already built for an OAuth failure, no new status
   value or new UI needed). `RepoSelector` stops fetching on its own mount
   entirely: it becomes a fully controlled component for this data too (no
   more internal `reposFetchStatus`/`reposRetryToken`/retry button, since a
   failure now never reaches `RepoSelector` in the first place). While this
   repos fetch is in flight, `LaunchLoader`'s accompanying message should read
   `repoListLoading` ("Cargando tus repositorios...", already exists as a key)
   instead of `stationSigningIn`, so the loader visually communicates which
   phase is actually happening; `Station.tsx` needs a small piece of state
   (e.g. which message key is currently active) to switch this text at the
   right moment without introducing a new `StationStatus` value, since the
   visual treatment (full-screen `LaunchLoader`) is identical for both phases.

## Round 3: only list repositories that already are MuunCode projects

Discussed and confirmed with the user: the existing-repo list must only ever show
repositories that already qualify as MuunCode projects, per this project's own
already-decided convention (`CLAUDE.md` -> "Configuration and Preferences":
project-level settings live in a committed `.MuunCode/workspace.json`). A repo
without that file is not a MuunCode project yet and must not appear in the
selectable list at all.

**Detection: GitHub's Code Search API, one call for the whole account, not one
call per repo.** `GET https://api.github.com/search/code?q=filename:workspace.json+path:.MuunCode+user:{login}`
(still GitHub's own REST API, `api.github.com`, no third-party service, same
auth token pattern already used everywhere else in this project) returns every
matching file across every repository the account has, in a single request; the
account's `login` comes from the same `GET /user/installations` call
`api/lib/githubInstallationId.ts` already makes (its response's
`installations[].account.login` field, not fetched today, needs to be returned
alongside the installation id). The `items[].repository.id` field in the search
response identifies which repos matched; `api/list-repos.ts` filters its
already-built, already-sorted repo array down to just those ids. This keeps the
whole operation at exactly one extra request per repo-list load, confirmed
acceptable given the Search API's own separate, stricter rate limit (10
requests/minute for an authenticated request, against the much higher limit
the rest of the REST API gets) is comfortably enough for one call per load; a
failure here folds into the exact same "the whole repo list failed to load"
path `list-repos.ts` already has (a `502` response), which the frontend already
turns into the full-screen rocket-loader error screen with its existing
retry-via-resign-in path -- no new retry mechanism needed.

**Zero matches is not an error.** If the search legitimately finds no matching
repos (a real GitHub account with zero MuunCode-shaped projects), `list-repos.ts`
still responds `200` with an empty array; this is a normal, valid outcome, not a
failure, so it must NOT trigger `Station.tsx`'s error screen. `RepoSelector.tsx`
needs a new empty-state view scoped to the existing-repo accordion section (not
a full-page takeover, this is not a fatal error) for when `repos.length === 0`:
a clear, warning-toned message (reusing the existing `WarningIcon` atom and this
app's already-established red-toned warning treatment,
`--color-neon-red`/`--color-card-bg-red` from `tokens.css`, rather than
inventing a new color token) reading (tagline + message, mirroring
`StatusScreen`'s own tagline/message split conceptually, just scoped smaller):
"Repositorios no aptos para ir a la Luna..." / "No se encontraron proyectos
hechos con MuunCode." (English: "No repositories fit for the Moon..." / "No
MuunCode projects found."), new i18n keys `repoListEmptyTagline`/
`repoListEmptyMessage`.

**Copy additions, to make the filtering visible/understood, not silent**: the
existing-repo hint and tab label both gain a `(Proyecto MuunCode)` /
`(MuunCode Project)` qualifier, so it is clear *why* only some repos show up,
without a separate explanatory paragraph:
- `repoSelectorHint` (es): "Selecciona uno de tus repositorios (Proyecto
  MuunCode), o crea uno nuevo." (en): "Pick one of your repositories (MuunCode
  Project), or create a new one."
- `existingRepoTabLabel` (es): "Seleccionar repositorio existente (Proyecto
  MuunCode)" (en): "Select existing repository (MuunCode Project)"

**Explicitly out of scope for this round**: validating the *contents* of
`.MuunCode/workspace.json` (schema/required fields like a selected device or
display) -- this round only checks the file's existence via search, per the
user's own framing ("solo es saber si tienen un archivo... y validar también
algunas cositas más" flagged as a later step, not this one). Also out of scope:
making the newly-created-repo flow (`api/create-repo.ts`) write this file
automatically -- this is a real, necessary follow-up (a freshly created repo
does not have `.MuunCode/workspace.json` yet, so it would not show up in this
same list on a future visit until it does), flagged here explicitly so it is
not forgotten, but left for its own separate round once this filtering round is
confirmed working, rather than bundling two rounds of GitHub Git Data API work
together.
